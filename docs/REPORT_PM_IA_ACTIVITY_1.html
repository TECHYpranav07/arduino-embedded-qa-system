Pre-Reflection of Activity

Prompt: Consider how collaborative platforms like GitHub can enhance transparency, traceability, and teamwork in solving real-world electronics and interdisciplinary project challenges.

In real-world electronics and embedded systems engineering, products involve tightly coupled interactions between firmware, circuit design, signal integrity, and hardware components. Traditional isolated development often creates communication silos where firmware faults are misdiagnosed as hardware defects and vice versa.

Platforms like GitHub provide:

  • Transparency: Complete auditability of every register configuration, interrupt handler, and timing parameter.
  • Deterministic Traceability: Linking commits to specific QA issues enables full historical tracing from the initial lab bug report to the verified patch.
  • Team Consensus & Safety: Pull requests and branch protections ensure that code changes undergo peer review and automated testing before reaching production, mitigating field failures.

C. QA Issues Logged (Problem Identification & Root Cause Analysis)

Four comprehensive engineering defects were identified, classified by severity, and analyzed using industry-standard 5-Why Analysis and Ishikawa (Fishbone) Diagrams:

1. [QA-01] Critical Timing Defect: Synchronous delay() Freezes MCU Execution

Critical (Sev-1) Closed in PR #5 View GitHub Issue #1

Symptom: Microcontroller becomes unresponsive to user push-button presses during 1000ms LED blinking cycles, resulting in an 87.5% input drop rate.

5-Why Root Cause Analysis:

  1. Why did the mode fail to switch? Digital Pin 2 was not read during physical button press.
  2. Why was Pin 2 not read? CPU was paused inside synchronous delay(1000) loops.
  3. Why was synchronous delay used? Prototype was written procedurally without task scheduling.
  4. Why was procedural design adopted? Initial focus was on rapid bring-up rather than concurrent I/O.
  5. Why was concurrency not built in? Root Cause: Absence of a non-blocking cooperative state machine architecture using millis().

2. [QA-02] Input Instability: Switch Contact Bounce & Floating Pin

High (Sev-2) Closed in PR #6 View GitHub Issue #2

Symptom: Tapping the push button once triggers 3 to 5 rapid mode increments due to mechanical chatter and high-impedance floating state.

Fishbone (Ishikawa) Root Cause Analysis:

                       CAUSE                                              EFFECT
 ---------------------------------------------------+
 Hardware / Components        Firmware / Software   |
   * Mechanical spring           * No debounce      |
     chatter (5-20ms)              filter window    |
   * Floating GPIO pin           * Polling raw pin  |
     (missing pull-up)             instantaneously  |
          \                             /           |
           \                           /            |
            +-------------------------+             +---> SPURIOUS MULTI-TRIGGERING
           /                           \            |     AND UNSTABLE MODE JUMPS
          /                             \           |
 Environment / Assembly       Process / Design      |
   * High EMI pickup             * Direct edge      |
     on breadboard wire            detection        |
   * Lack of bypass cap            without time     |
     across switch contacts        hysteresis       |
 ---------------------------------------------------+

Root Cause: Lack of internal pull-up resistor configuration and missing 50ms temporal debounce filter.

3. [QA-03] Electrical Stress: Unclamped 100% Duty Cycle Overcurrent

High (Sev-2) Closed in PR #7 View GitHub Issue #3

Symptom: Continuous full 100% duty cycle illumination in Mode 1 draws sustained 20.67 mA, leading to localized heating on the ATmega328P output driver.

5-Why Root Cause Analysis:

  1. Why does the pin run hot? Sourcing continuous maximum DC current.
  2. Why is maximum current sustained? Driven constantly with binary digitalWrite(LED_PIN, HIGH).
  3. Why was binary driving used? Hardware PWM pin capabilities (OC1A) were not utilized.
  4. Why was power dissipation overlooked? Component reliability derating guidelines were omitted.
  5. Why were derating rules omitted? Root Cause: Absence of firmware-level power throttling and PWM duty cycle clamping.

4. [QA-04] Telemetry & Communication Defect: UART Buffer Saturation & CPU Stall

Medium (Sev-3) Closed in PR #8 View GitHub Issue #4

Symptom: Unregulated Serial.print() in every loop cycle saturated the 64-byte hardware TX buffer within 2 milliseconds, dropping loop execution frequency from 48 kHz to 24 Hz.

Root Cause: Unthrottled telemetry streaming at 50 kHz cycle rates over a 9600 bps UART channel lacking a periodic heartbeat scheduler.
